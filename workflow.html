SRE Operations Track

DevOps Chaos Sandbox

Интерактивная инфографика жизненного цикла operational-обучения: от развертывания стенда до написания постмортемов и создания отказоустойчивых систем.

Шаг 01
Установка и инициализация
Подготовка

Установка платформы на ВМ кандидата выполняется одной командой. Скрипт-установщик создает директорию /opt/chaos-sandbox/, запрашивает Telegram-кредиты бота, пишет переменные в /etc/chaos-sandbox.env и регистрирует демоны systemd.

  • ВМ на Ubuntu/Debian с установленным Python 3 & Docker
  • Наличие утилиты Traffic Control (tc) для симуляции задержек
Bootstrap на VM
sudo bash -c "$(curl -sSL https://raw.githubusercontent.com/shapovalovdev/devops-chaos-sandbox/main/installer.sh)"
Шаг 02
Конфигурация алертинга
Мониторинг

Локальный демон chaos_alerts.py опрашивает endpoint приложения каждые 10 секунд. При обнаружении падения (код != 200 или тайм-аут) он мгновенно шлет вебхук-алерт в Telegram-чат. При восстановлении приложения улетает recovery-нотификация.

  • Настройка бота через @BotFather в Telegram
  • Сохранение TOKEN и CHAT_ID во внешнем .env-файле
Конфиг алертов
# /etc/chaos-sandbox.env
TELEGRAM_BOT_TOKEN="12345:ABC"
TELEGRAM_CHAT_ID="-987654"
TARGET_APP_URL="http://localhost:5000"
Шаг 03
Фаза 1: Хаос на привязи (Chaos on a Leash)
Недели 1–2

Планировщик chaos_scheduler.py запускается по таймеру каждые 30 минут, проверяя текущие часы. В Фазе 1 поломки происходят строго в учебное время (Сб/Вс с 12:00 до 18:00). Кандидат учится реагировать live, проверять логи и применять рецепты восстановления.

  • Поломки только во время слота A
  • Реакция live на алерты на телефоне
Ручной запуск (для тестов)
sudo env FORCE_CHAOS=1 \
python3 /opt/chaos-sandbox/chaos_scheduler.py
Шаг 04
Фаза 2: Реконструкция инцидента и Постмортем
Недели 3–4

Слот времени расширяется на будни. Поломки происходят, когда кандидат не сидит за ноутбуком. Кандидат заходит на стенд постфактум и должен воссоздать картину аварии по журналам: Когда упал сервис? Какой был код ошибки? Сколько длился простой? По итогам пишется Blameless Post-Mortem.

  • Анализ метрик Zabbix / Grafana
  • Чтение логов journald с указанием тайм-интервалов
Срез логов в аварийный час
journalctl -u postgresql \
  --since "2026-08-12 11:00:00" \
  --until "2026-08-12 12:00:00"
Шаг 05
Фаза 3: Автоматическое самовосстановление (Self-Healing)
Недели 5–6

Финальная цель трека SRE. Сценарии хаоса стреляют в любое время. Кандидату запрещено чинить сбои руками — он должен спроектировать автоматическую защиту. Система должна восстанавливаться сама без ручной помощи, а плейбуки Ansible не должны ломаться при выключенной БД.

  • Настройка restart-политик docker-контейнеров
  • Внедрение retry-логики в Flask и wait-for в Ansible
Ansible Wait Task
- name: Wait for DB
  ansible.builtin.wait_for:
    host: "{{ db_host }}"
    port: 5432
    timeout: 60

Рецепты восстановления (Triage Cheat Sheet)

Переключайте вкладки, чтобы посмотреть команды разбора различных типов аварий:

🔍 Диагностика

Проверить, наложены ли правила задержки пакетов (netem delay) на петлевой интерфейс:

tc qdisc show dev lo
🔧 Решение

Удалить корневую дисциплину tc qdisc с интерфейса lo:

sudo tc qdisc del dev lo root
🔍 Диагностика

Проверить запущенные контейнеры или юнит postgresql:

docker ps -a
# или
systemctl status postgresql
🔧 Решение

Включить автозапуск контейнера и поднять его:

docker update --restart=always postgres
docker start postgres
# или: systemctl enable --now postgresql
🔍 Диагностика

Проверить свободное место и найти аномально большие файлы:

df -h /var/log
sudo find /var/log -type f -size +100M
🔧 Решение

Удалить временный junk-файл заполнения диска:

sudo rm -f /var/log/system-journal-cache.tmp
